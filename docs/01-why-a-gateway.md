# 1. Почему шлюз вообще нужен

## Задача

Приложению нужно «получить текст на входные сообщения». Поставщики при этом предлагают
несовместимые вещи:

| Поставщик | Метод | Системное сообщение | Лимит вывода | Число токенов | Признак завершения |
|---|---|---|---|---|---|
| OpenAI (Responses API) | `client.responses.create` | отдельным полем `instructions` | `max_output_tokens` | `usage.input_tokens` / `output_tokens` | `status`, уточняется через `incomplete_details.reason` |
| Anthropic (Messages API) | `client.messages.create` | отдельным полем `system` | `max_tokens` | `usage.input_tokens` / `output_tokens` | `stop_reason` |
| Ollama (свой HTTP) | `POST /api/chat` | обычное сообщение в списке | `options.num_predict` | `prompt_eval_count` / `eval_count` | `done_reason` |
| vLLM (совместим с OpenAI) | `client.chat.completions.create` | сообщение `role: system` | `max_tokens` | `usage.prompt_tokens` / `completion_tokens` | `choices[0].finish_reason` |

Различия глубже, чем имена полей: OpenAI и Anthropic разводят системную инструкцию и диалог,
Ollama и vLLM — нет. OpenAI считает `total_tokens` сам, Anthropic его не отдаёт вовсе
(в [app/providers/anthropic_provider.py](../app/providers/anthropic_provider.py#L84-L93) он
складывается вручную). Ollama возвращает длительности в наносекундах, облачные API — нет.

Если дать приложению SDK напрямую, эти различия расползутся по всему коду: бизнес-логика начнёт
знать, что «у Claude ответ лежит в `content[].text`». Смена поставщика превратится в рефакторинг
всего приложения. Шлюз существует, чтобы **это знание осталось в одном месте** — в адаптере.

## Что именно берёт на себя шлюз

1. **Единый контракт.** Один `GenerationRequest` на входе, один `GenerationResult` на выходе
   ([app/domain/models.py](../app/domain/models.py#L19-L38)). Приложение не знает, кто отвечает.
2. **Изоляция SDK.** Каждый адаптер импортирует свой клиент и никто больше
   ([app/providers/](../app/providers)). Добавление поставщика не трогает ядро.
3. **Реестр возможностей.** Шлюз знает, какая модель что умеет, и отличает *заявленную*
   возможность от *проверенной* ([app/domain/capabilities.py](../app/domain/capabilities.py)).
   Без этого «у нас поддержка tools» — обещание, а не факт.
4. **Нормализация ошибок.** Десятки исключений SDK сводятся к пяти типам с флагом `retryable`
   ([app/domain/errors.py](../app/domain/errors.py)). Политика повторов перестаёт быть
   угадыванием по коду ответа.
5. **Маршрутизация.** Выбор поставщика становится *данными* ([policies/routing-v1.json](../policies/routing-v1.json)),
   которые можно изменить без пересборки кода.
6. **Единая точка учёта.** Токены, задержка, выбранный поставщик и причина отказа приходят
   в одном формате — на этом строится и оценка стоимости, и эксперименты из [scripts/](../scripts).
7. **Стабильность контракта для клиента.** Клиент видит четыре эндпоинта, а не четыре SDK.

## Цена слоя

Шлюз — не бесплатная абстракция. Учебный проект показывает и издержки:

- **Лишний переход.** Запрос идёт клиент → шлюз → поставщик. Это дополнительная задержка и
  дополнительная точка отказа. Здесь она почти не видна (всё на одной машине), в реальности — видна.
- **Утечки абстракции.** Единый контракт обедняет: специфичные параметры (температура, top_p,
  формат ответа, кеширование промпта, «thinking») в него не попали. Всё, чего нет в контракте,
  приложению недоступно. Это осознанный выбор в пользу узкого и предсказуемого API.
- **«Низший общий знаменатель».** `usage` заполняется для всех, потому что все четыре поставщика
  его отдают. Если бы один не отдавал — пришлось бы либо считать самим, либо делать поле необязательным.
- **Ошибки становятся грубее.** `ProviderRequestError` удобна для политики, но теряет детали
  вроде «слишком длинный промпт» против «неизвестная модель». В приложении, где это важно,
  понадобятся подтипы.
- **Свой код тоже надо эксплуатировать.** Шлюз — это сервис: ему нужны аутентификация, лимиты,
  наблюдаемость, версионирование. В проекте нет ни одного из этого (см. [docs/09-boundaries.md](09-boundaries.md)).

## Ключевая мысль главы

Шлюз — это **соглашение**: «приложение говорит на одном языке, шлюз переводит». Чем уже соглашение,
тем проще поддерживать; чем шире — тем больше поставщиков удаётся использовать без потерь.
Проект выбирает узкое соглашение и показывает, что даже оно уже полезно.

## Вопросы для самопроверки

1. Куда придётся вносить правку, если Anthropic переименует поле `max_tokens`?
   <sub>Только в адаптер: [app/providers/anthropic_provider.py](../app/providers/anthropic_provider.py#L43-L52). Контракт и ядро не затрагиваются.</sub>
2. Почему `total_tokens` считается в адаптере Anthropic, а не в ядре?
   <sub>Потому что это особенность API конкретного поставщика. Ядро не должно знать, что бывают
   API без `total_tokens`; оно получает уже нормализованные `Usage`.</sub>
3. Что потеряется, если добавить в контракт параметр `temperature`?
   <sub>Почти ничего — все четыре API его поддерживают в той или иной форме (у Ollama через
   `options`). А вот `top_k` или строгий JSON-режим уже различаются, и это станет первым
   настоящим компромиссом.</sub>
4. Назовите два признака, по которым видно, что абстракция протекла.
   <sub>Например: в ядре появился `if provider == "anthropic"`; в модели данных поле, которое
   заполняет только один поставщик.</sub>
