# 7. Ошибки и коды ответов

## Таксономия

Все ошибки шлюза наследуются от одного класса с единственным обязательным решением —
имеет ли смысл повтор:

```python
class GatewayError(Exception):
    def __init__(self, message: str, *, retryable: bool) -> None:
        super().__init__(message)
        self.retryable = retryable
```

[app/domain/errors.py](../app/domain/errors.py#L1-L5)

`retryable` — **свойство ошибки**, а не решение обработчика. Это ключевая мысль: адаптер знает
про поставщика больше, чем любой вызывающий код, и именно он должен сказать «это пройдёт само»
или «это не пройдёт никогда».

| Тип | Когда возникает | `retryable` | Смысл |
|---|---|---|---|
| `ProviderAuthenticationError` | 401/403 от поставщика | нет | ключ неверный или доступ запрещён |
| `ProviderRequestError` | 400/404/422 | нет | запрос невалиден для этой модели |
| `ProviderRateLimitError` | 429 | да | лимит частоты |
| `ProviderUnavailableError` | 5xx, обрыв, таймаут | да | поставщик временно недоступен |
| `InvalidProviderResponseError` | 200, но ответ не разобрать | нет | поставщик нарушил контракт |
| `UnsupportedModelError` | модель не та, что настроена | нет | ошибка конфигурации клиента |
| `RoutingConfigurationError` | политика битая или невозможная | нет | ошибка конфигурации шлюза |

[app/domain/errors.py](../app/domain/errors.py#L7-L65)

Обратите внимание на `InvalidProviderResponseError`: ответ пришёл, статус `200`, но текста или
статистики нет. Повторять бессмысленно — поставщик уже сказал «всё хорошо» и соврал. Именно
поэтому это отдельный тип, а не «недоступность».

## Отображение в HTTP

Схема ответа об ошибке одна на оба эндпоинта:

```python
def provider_http_error(error: GatewayError, status_code: int) -> HTTPException:
    return HTTPException(
        status_code=status_code,
        detail={"message": str(error), "retryable": error.retryable},
    )
```

[app/api/routes/generation.py](../app/api/routes/generation.py#L90-L100)

`retryable` дублируется в теле намеренно: клиент не должен угадывать по коду ответа, повторять
ему запрос или нет. `503` — почти всегда повторяемо, `400` — почти никогда, но «почти» здесь
недостаточно.

### `POST /generate`

| Тип ошибки | Код | Пример ситуации |
|---|---|---|
| `UnsupportedModelError` | `400` | запрос с `not-my-model` |
| `ProviderRequestError` | `400` | слишком длинный промпт |
| `ProviderRateLimitError` | `503` | исчерпана квота |
| `ProviderUnavailableError` | `503` | таймаут, 5xx |
| остальные `GatewayError` | `502` | `ProviderAuthenticationError`, `InvalidProviderResponseError` |

[app/api/routes/generation.py](../app/api/routes/generation.py#L113-L125)

Проверено на живом сервисе:

```json
{
  "detail": {
    "message": "Модель not-my-model не настроена для поставщика ollama. Ожидается qwen3:0.6b-q4_K_M",
    "retryable": false
  }
}
```

### `POST /generate/auto`

| Тип ошибки | Код |
|---|---|
| `RoutingConfigurationError` | `500` |
| `ProviderRequestError` | `400` |
| `ProviderRateLimitError` / `ProviderUnavailableError` | `503` |
| остальные `GatewayError` | `502` |

[app/api/routes/generation.py](../app/api/routes/generation.py#L135-L147)

Различие между эндпоинтами осмысленно: для `/auto` отсутствие работающей политики — это `500`,
потому что запрос клиента корректен, а сломано у нас. Для `/generate` неверная модель — вина
запроса, то есть `400`.

## Два уровня, которые не видны в таблице

### `422` — до всякого кода

Некорректная схема отклоняется Pydantic до вызова обработчика, и формат ответа другой —
без `retryable`:

```json
{
  "detail": [
    {
      "type": "literal_error",
      "loc": ["query", "provider"],
      "msg": "Input should be 'openai', 'anthropic', 'ollama' or 'vllm'",
      "input": "gemini"
    }
  ]
}
```

То есть у клиента шлюза три разных формата ошибки: `422` от FastAPI, `{"detail":{"message","retryable"}}`
от шлюза и стандартные `5xx`-исключения. Унификация — очевидное улучшение, но проект её не делает,
чтобы каждый уровень оставался видимым как есть.

### `500` — то, что никто не поймал

Всё, что не является `GatewayError`, уходит наружу без обработки: `AttributeError` в адаптере,
ошибка в самом шлюзе. Это правильное поведение — маскировать собственные баги не нужно, — но
означает, что `500` в `/generate/auto` это ещё и «адаптер нарушил контракт».

## Что можно критиковать в этой схеме

Проект ценно читать не только как образец, но и как предмет разбора:

1. **`401` от поставщика отдаётся как `502`.** С точки зрения клиента это не его вина, но и не
   «плохой шлюз» — это наша конфигурация. Здесь скорее просится `500` с явным текстом
   «ключ поставщика отклонён», иначе дежурный ищет проблему в сети.
2. **Нет машиночитаемого кода ошибки.** Есть текст на русском и `retryable`. Клиент не может
   надёжно отличить «квота» от «сеть», не разбирая строку. `code: "provider_rate_limit"` стоил бы
   одну строку.
3. **Нет `Retry-After`.** Для `429` это прямое указание поставщика, и терять его жалко.
   `ProviderRateLimitError` не сохраняет исходное исключение в доступном виде (только `__cause__`).
4. **Ошибка полного отказа маршрута теряет журнал.** Когда все кандидаты упали, клиент видит
   только последнюю ошибку; массив `attempts` существует лишь в успешном ответе
   ([app/gateway/routing.py](../app/gateway/routing.py#L71-L92)). В реальной эксплуатации нужен
   ответ с историей попыток и кодом `502`/`503`.
5. **Нет идентификатора запроса.** Сопоставить ошибку клиента с записью в логах шлюза нечем.

## Вопросы для самопроверки

1. Поставщик ответил `200`, `usage` есть, `output_text` пустая строка. Какой тип ошибки и почему
   не `ProviderUnavailableError`?
   <sub>`InvalidProviderResponseError`, `retryable = false`: контракт нарушен, повтор даст то же
   самое. Недоступность означала бы, что ответа нет вовсе.</sub>
2. Клиент получил `503` и сразу повторил запрос десять раз. Что произойдёт с точки зрения
   маршрутизации?
   <sub>Ничего хорошего: шлюз не имеет ограничителя, каждый запрос снова проходит по кандидатам,
   и все десять попадут в недоступный поставщик. Квоты и лимиты — вне проекта,
   см. [docs/09-boundaries.md](09-boundaries.md).</sub>
3. Почему `RoutingConfigurationError` наследуется от `GatewayError`, а не от `RuntimeError`?
   <sub>Чтобы попасть в общий `except GatewayError` и получить единый формат ответа. Побочный
   эффект: такой ошибке пришлось явно назначить `retryable=False`.</sub>
4. Как бы вы добавили `code` в ответ, не меняя адаптеры?
   <sub>Словарём «тип исключения → код» в `provider_http_error` и полем `code` в `detail`.
   Адаптерам знать об этом не нужно — таксономия уже нормализована.</sub>
