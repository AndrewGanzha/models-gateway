# 5. Реестр возможностей

## Проблема

Документация поставщика обещает многое. Модель, скачанная в Ollama, может не поддерживать
tool calling; локальная сборка может терять структурированный вывод; «совместимый с OpenAI»
сервер может не реализовывать нужный эндпоинт. Если шлюз верит документации, он передаёт клиенту
обещание, которое не может выполнить.

Поэтому в проекте **возможность — это не флаг, а утверждение с уровнем доверия**.

## Модель данных

```python
class CapabilityState(str, Enum):
    SUPPORTED = "supported"
    UNSUPPORTED = "unsupported"
    LIMITED = "limited"
    UNKNOWN = "unknown"

class CapabilityInfo(BaseModel):
    declared: bool | None = None
    verified: CapabilityState = CapabilityState.UNKNOWN
    note: str | None = None
```

[app/domain/capabilities.py](../app/domain/capabilities.py#L6-L19)

Два независимых поля — суть идеи:

- `declared` — что говорит поставщик (может быть `None`, если и не говорит ничего);
- `verified` — что установлено в этой конфигурации.

`UNKNOWN` — не «нет», а «не проверяли». Это позволяет отличать «мы не умеем» от «мы не знаем»,
и не давать клиенту ложной уверенности ни в одну сторону.

Модель реестра неизменяема (`frozen=True`) и запрещает лишние поля (`extra="forbid"`):
возможности — справочник, а не место для накопления случайных данных
([#L21-L31](../app/domain/capabilities.py#L21-L31)).

## Реестр

[app/gateway/model_registry.py](../app/gateway/model_registry.py) собирает словарь
«имя поставщика → описание модели». Здесь видно принципиальное решение: у каждого поставщика
ровно **одна** настроенная модель, и она берётся из окружения, а не из кода.

```python
"ollama": ModelCapabilities(
    provider="ollama",
    model=ollama_model,
    text_generation=verified_ollama_generation,
    structured_output=declared_but_not_verified,
    tools=declared_but_not_verified,
    streaming=declared_but_not_verified,
)
```

[#L52-L59](../app/gateway/model_registry.py#L52-L59)

Состояние всех четырёх моделей в этой конфигурации:

| Возможность | Состояние | Смысл |
|---|---|---|
| `text_generation` | `SUPPORTED` | проверено настоящими запросами |
| `structured_output` | `UNKNOWN` | заявлено, но не проверялось |
| `tools` | `UNKNOWN` | заявлено, но не проверялось |
| `streaming` | `UNKNOWN` | заявлено, но не проверялось |

Проверить можно у себя:

```bash
curl -s http://127.0.0.1:8001/models | python -m json.tool
```

## Где выполняется проверка

Возможности — не декоративная справка. Маршрутизатор отказывается использовать поставщика,
если генерация текста не подтверждена:

```python
verified = gateway.capabilities.text_generation.verified
if verified != CapabilityState.SUPPORTED:
    raise RoutingConfigurationError(
        f"Генерация текста не подтверждена для {provider_name}"
    )
```

[app/gateway/routing.py](../app/gateway/routing.py#L117-L123)

Заметьте: проверка выполняется **в конструкторе** `ModelRouter`, то есть при старте
([#L52-L53](../app/gateway/routing.py#L52-L53)). Политика, ссылающаяся на непроверенную модель,
не пустит приложение в работу — это лучше, чем обнаружить проблему на живом запросе.

Обратите внимание на асимметрию: это проверка *способности выполнить работу*, а не *поддержки
параметров*. Шлюз не проверяет `tools`, потому что и не использует их.

## Как возможность становится проверенной

Только запросом, который демонстрирует результат. В проекте это делали скрипты оценки: они
обращались к `/generate` по каждому поставщику, и только после реальных ответов в реестре
появилось `SUPPORTED` с пометкой «Проверено настоящими запросами»
([app/gateway/model_registry.py](../app/gateway/model_registry.py#L14-L33)).

Правильный процесс для новой возможности:

1. заявлено (`declared = True`, `verified = UNKNOWN`) — её видно, но ею нельзя пользоваться;
2. есть проверка в автоматическом прогоне;
3. прогон зелёный — `verified = SUPPORTED` с пометкой, чем именно проверено;
4. прогон красный — `UNSUPPORTED` с пометкой, что именно не работает.

Шаг 4 важнее, чем кажется: `UNSUPPORTED` защищает от повторных попыток и от «а может, попробуем
ещё раз». Именно этого поля не хватает в текущем проекте — все возможности либо `SUPPORTED`,
либо `UNKNOWN`.

## Чего в модели нет

- **Даты и версии проверки.** `note` — строка, а не дата. Сравнить две модели по «свежести»
  проверки нельзя.
- **Использования `LIMITED`.** Состояние объявлено, но не применяется: нет ни одной возможности,
  которая «работает частично». Хороший пример того, как модели данных опережают реальность —
  и почему неиспользуемые значения лучше всё-таки удалять или заполнять.
- **Условий применимости.** `structured_output: UNKNOWN` не говорит, для каких схем вывод
  проверялся.

## Вопросы для самопроверки

1. Чем `verified: "unknown"` отличается от `declared: false`?
   <sub>`unknown` — мы не знаем; `declared: false` — поставщик отрицает, то есть знаем, что не
   поддерживается. Первое требует проверки, второе — нет.</sub>
2. Что произойдёт, если в `policies/routing-v1.json` указать `"ollama"`, но у Ollama поставить
   `text_generation.verified = UNKNOWN`?
   <sub>Приложение не запустится: конструктор `ModelRouter` бросит `RoutingConfigurationError`.
   Ошибка будет видна в логах старта, а не на запросе.</sub>
3. Почему реестр — статический словарь, а не запрос к поставщикам при старте?
   <sub>Потому что «умеет» — свойство модели в этой конфигурации, а не ответ API. Живая проверка
   при старте давала бы случайные отказы (сеть, квоты) и тормозила запуск. Проверка — отдельная
   задача с отдельными артефактами, см. [docs/08-evaluation.md](08-evaluation.md).</sub>
4. Как добавить в реестр возможность «контекст: 128k токенов», чтобы она была полезной?
   <sub>Отдельным полем с числом, а не `CapabilityInfo`: это не «умеет/не умеет». И проверить
   на реальном длинном промпте, иначе это цифра из документации.</sub>
