# 6. Маршрутизация и резерв

## Политика — данные, а не код

```json
{
  "version": "routing-v1",
  "candidates": ["openai", "anthropic"],
  "max_attempts": 2
}
```

[policies/routing-v1.json](../policies/routing-v1.json)

Модель политики строгая: лишние поля запрещены, `version` обязательна, `candidates` непустой,
`max_attempts > 0` ([app/domain/routing.py](../app/domain/routing.py#L8-L13)).

Файл читается один раз при импорте, и любая проблема — отсутствующий файл, битый JSON,
несоответствие схеме — превращается в `RoutingConfigurationError`
([app/gateway/routing.py](../app/gateway/routing.py#L23-L32)). Это пример «падать при старте,
а не на трафике»: конфигурация, которую нельзя прочитать, не должна пропускать запросы.

`version` — не украшение. Она возвращается клиенту в каждом ответе маршрутизации
(`route_version`), поэтому по ответу можно понять, какой политикой он получен. Для инцидентов
и экспериментов это дешевле, чем восстанавливать конфигурацию по логам.

## Как строится список кандидатов

```python
self._candidates = policy.candidates[: policy.max_attempts]
if len(set(self._candidates)) != len(self._candidates):
    raise RoutingConfigurationError("Политика содержит повторяющихся кандидатов")
```

[app/gateway/routing.py](../app/gateway/routing.py#L43-L50)

Две мелочи с большими последствиями:

- **`max_attempts` — это и лимит попыток, и длина среза.** Политика «три кандидата, две попытки»
  валидна и означает «третий не пригодится». Логика защищает от случайного «попробуем всех по кругу».
- **Дубликаты запрещены.** Без этой проверки `["openai", "openai"]` выглядело бы как резерв,
  но это был бы повтор того же поставщика — то есть скрытый retry, который политика и пытается
  контролировать.

Каждый кандидат проверяется конструктором: он должен существовать среди шлюзов и иметь
подтверждённую генерацию текста ([#L52-L53](../app/gateway/routing.py#L52-L53),
[#L110-L123](../app/gateway/routing.py#L110-L123)).

## Алгоритм попыток

```python
for position, provider_name in enumerate(self._candidates):
    gateway = self._get_gateway(provider_name)
    ...
    try:
        result = await gateway.generate(generation_request)
    except GatewayError as error:
        attempts.append(RoutingAttempt(provider=provider_name, status="failed", error=str(error)))
        can_use_fallback = (
            error.retryable
            and position + 1 < len(self._candidates)
            and current_state.can_switch
        )
        if can_use_fallback:
            continue
        raise
```

[app/gateway/routing.py](../app/gateway/routing.py#L63-L104)

Четыре решения в этих строках:

1. **Модель берётся из реестра, а не от клиента.** `gateway.capabilities.model` — маршрутизатор
   не спрашивает «какую модель», он спрашивает «какой поставщик». Клиентский `RoutedGenerationRequest`
   вообще не содержит поля `model` ([app/domain/routing.py](../app/domain/routing.py#L30-L34)).
2. **Ловится только `GatewayError`.** Программная ошибка не маскируется под отказ поставщика —
   она падает наружу как `500`. Это правильный компромисс: скрывать собственные баги за резервом
   было бы вредно.
3. **Переключение только при `retryable`.** Неверный ключ, неизвестная модель или кривой запрос
   не лечатся сменой поставщика ([docs/07-errors.md](07-errors.md)).
4. **Журнал попыток.** Каждая попытка попадает в `attempts`, включая успешную. Ответ становится
   самоописывающим.

## Вторая линия защиты: `RoutingState`

```python
class RoutingState(BaseModel):
    output_started: bool = False
    external_action_completed: bool = False

    @property
    def can_switch(self) -> bool:
        return not (self.output_started or self.external_action_completed)
```

[app/domain/routing.py](../app/domain/routing.py#L16-L27)

Это самая интересная часть главы, хотя в текущем коде флаги никто не выставляет — сегодня они
всегда `False`, потому что потоковой выдачи нет.

Зачем тогда они? Потому что это **предохранитель против неидемпотентного повтора**. Представьте,
что добавлена потоковая выдача: клиент уже получил первые токены. Переключение на другого
поставщика означало бы либо склейку двух разных ответов, либо отмену уже показанного текста.
А `external_action_completed = True` (модель вызвала инструмент, деньги списаны, письмо отправлено)
означает, что повтор создаст второе действие.

Формулировка из решения:

> Резерв разрешён только после временной ошибки и до начала ответа или выполнения внешнего действия.

[decisions/routing-v1.md](../decisions/routing-v1.md#L13-L14)

Проект фиксирует правило раньше, чем появляется функциональность, которая его нарушит. Это
учебная ценность кода: инвариант записан и проверяем, даже когда он тривиально выполняется.

## Чем маршрутизация здесь не является

Полезно перечислить, потому что в индустрии под словом «routing» понимают разное:

| Не реализовано | Что это дало бы | Почему отсутствует здесь |
|---|---|---|
| Взвешенное распределение трафика (канареечное развёртывание) | сравнение моделей на реальном трафике | учебная задача — показать выбор, а не статистику |
| Маршрут по содержимому (классификация запроса) | дешёвая модель для простого, дорогая для сложного | в проекте для классификации уже используется модель, это было бы вложенно |
| Учёт бюджета и квот | остановка трат | требует хранилища и состояния |
| Проверка здоровья поставщика | отказ до запроса, а не после таймаута | усложняет ядро; сейчас отказ обнаруживается первой попыткой |
| Приоритет по цене модели | экономия | цена здесь учтена при выборе порядка, а не в рантайме |

Порядок кандидатов — линейный и статический. Это сознательная простота: политика читается
за пять секунд и полностью объясняет поведение системы.

## Откуда взялся именно такой порядок

Не из интуиции. Из измерений и записанного решения
([decisions/routing-v1.md](../decisions/routing-v1.md)):

- обе модели показали одинаковую точность на наборе (8/8);
- OpenAI дешевле — по снимку тарифов примерно в семь раз
  ([evals/pricing-proxyapi-2026-10-02.json](../evals/pricing-proxyapi-2026-10-02.json));
- Anthropic быстрее (677 мс против 2 171 мс) и остаётся приемлемым по качеству.

Отсюда «основной — дешёвый, резервный — быстрый». Обратите внимание: критерий резерва не «тоже
дешёвый», а «другой по свойствам». Резерв нужен, когда основной недоступен, и тогда важна
не цена, а способность ответить.

В том же решении записано, какие варианты отвергнуты и при каких условиях правило пересматривается
([#L22-L31](../decisions/routing-v1.md#L22-L31)). Это превращает конфигурацию в решение с
областью применимости, а не в «так исторически сложилось».

## Вопросы для самопроверки

1. Политика `{"candidates": ["openai", "anthropic"], "max_attempts": 1}`. Что изменится?
   <sub>Резерв отключён: срез даст `["openai"]`, второй кандидат не рассматривается, `anthropic`
   не будет использован никогда.</sub>
2. Поставщик вернул `429`. Будет резерв?
   <sub>Да: `ProviderRateLimitError.retryable = True`, есть следующий кандидат, `can_switch = True`.</sub>
3. Поставщик вернул `401`. Резерв?
   <sub>Нет: `ProviderAuthenticationError.retryable = False`, ошибка пробрасывается. Это и есть
   смысл решения «переключение после любой ошибки скрывало бы ошибки ключей».</sub>
4. Все кандидаты отказали с `retryable`-ошибкой. Что увидит клиент?
   <sub>Исключение последнего кандидата, отображённое в `503`. Журнал `attempts` при этом теряется —
   он не попадает в тело ответа, только в текст исключения. Это ограничение текущего дизайна:
   при полном отказе клиент не видит всей картины.</sub>
5. Почему `route_version` возвращается клиенту, а не только пишется в лог?
   <sub>Потому что поведение системы зависит от политики, и по ответу должно быть видно, какая
   политика его произвела. Без этого A/B-сравнение политик невозможно.</sub>
